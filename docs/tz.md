# Технічне завдання на систему моніторингу насосного агрегату

## Мета та межі системи

Оператор насосної станції має бачити, чи працює насос, переглядати історію його показників і отримувати сповіщення про підвищену вібрацію. Навчальний стенд охоплює один програмно змодельований насос, шлюз збору даних і сервер обробки телеметрії. Фізичне керування двигуном та аварійне вимкнення насоса виходять за межі системи.

**Зацікавлені сторони.** Оператор стежить за станом агрегату. Інженер з обслуговування використовує історію вимірювань для оцінки зносу. Розробник перевіряє поведінку системи на відтворюваних сценаріях.

## Архітектура та інтерфейси

| Шар | Шлях даних |
|---|---|
| Edge | Симулятор насоса → шлюз із локальним буфером → публікація через MQTT |
| Сервер | MQTT-брокер → сервіс запису → база даних SQLite |
| Сервер | Той самий брокер → рушій правил → тема MQTT зі сповіщеннями для оператора |
| Сервер | MQTT-брокер → модуль аналітики → виявлення аномалій та оцінка залишкового ресурсу підшипника (RUL) |

У завершеній системі передбачено автентифікацію, правила доступу (ACL), підпис повідомлень і розгортання сервісів через Docker Compose.

Метод `PumpSimulator.step(dt=1.0, now=None)` повертає словник із полями `device_id` (ідентифікатор насоса), `ts` (секунди Unix), `running` (ознака роботи) та `metrics` (числові показники). Шлюз передає словник як JSON у тему `plant/{site}/{line}/{device}/telemetry` із QoS 1. Для сповіщень останній сегмент теми змінюється на `alerts`.

## Функціональні вимоги

| Код | Вимога |
|---|---|
| FR-1 | Кожний виклик `step()` формує один запис із чотирма показниками: вібрація `vibration_mm_s` (мм/с), температура підшипника `temperature_c` (°C), тиск на виході `pressure_bar` (бар), струм двигуна `current_a` (А). |
| FR-2 | Симулятор підтримує зупинку та дві несправності. Після зупинки тиск і струм дорівнюють 0. Несправність `bearing` встановлює знос щонайменше 0,7. Для `clog` середній тиск за 30 кроків нижчий, а середній струм вищий, ніж у справного насоса за того самого seed. |
| FR-3 | За справного з’єднання шлюз публікує телеметрію одного насоса з частотою 1 повідомлення за секунду. |
| FR-4 | Сервер зберігає ідентифікатор, час і всі чотири показники кожного з 60 різних повідомлень контрольної серії. |
| FR-5 | Після трьох послідовних вимірів вібрації понад 4,5 мм/с система формує одну подію `raised`. Коли вібрація падає нижче 4,0 мм/с, система формує одну подію `cleared`. |

## Нефункціональні вимоги

| Код | Вимога |
|---|---|
| NFR-1 | Відтворюваність: для двох симуляторів з однаковими параметрами, seed, командами й часовими мітками збігаються всі 100 зі 100 послідовних записів. |
| NFR-2 | Стійкість до обриву зв’язку: за частоти 1 Гц і перерви у зв’язку на 60 с усі 60 унікальних записів після відновлення з’єднання доходять до брокера в порядку вимірювання. Шлюз протягом перевірки працює без перезапуску. |
| NFR-3 | Затримка на локальному стенді: щонайменше 95 зі 100 записів з’являються в базі протягом 3 с від моменту вимірювання. |
| NFR-4 | Сумісність даних: усі 100 зі 100 повідомлень контрольної серії після кодування в JSON і декодування зберігають назви полів, типи та початкові значення. |

## Обмеження та ризики

Стенд працює на одному ПК із Python 3.10 або новішим. Час вимірювання та запису береться з одного системного годинника. Випадковий шум може спотворити порівняння окремих показників, тому несправність перевіряють за серією вимірів із фіксованим seed. Тривалий розрив зв’язку може переповнити буфер шлюзу, тому для перевірки NFR-2 його місткість має бути не меншою за 60 записів.

## Критерії приймання

1. **Симулятор, лабораторна № 1 (FR-1, FR-2, NFR-1).** Виконати автотести командою `python -m pytest tests/test_lab1_sim.py -v`. Перевірити склад запису, окремо відтворити зупинку й обидві несправності та порівняти два прогони по 100 кроків із фіксованими часовими мітками.
2. **Передавання і збереження (FR-3, FR-4, NFR-2–NFR-4).** Записати 100 повідомлень за 100 с, перевірити JSON і затримку кожного запису. Для перших 60 повідомлень звірити всі показники з базою. Окремо від’єднати брокер на 60 с і після підключення звірити послідовність часових міток із буферизованою серією.
3. **Сповіщення (FR-5).** Подати значення вібрації 4,6 → 4,7 → 4,8 → 4,9 → 3,9 мм/с. Очікувані події: `raised` на третьому вимірі та `cleared` на п’ятому. На решті вимірів нові події відсутні.
